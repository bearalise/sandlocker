# SandLocker M0 技术验证计划

| 项目 | 内容 |
| --- | --- |
| 版本 | v1.0 |
| 日期 | 2026-08-01 |
| 依据 | PRD v1.2（第 11 章 M0 行、ADR-4/12/13/18/23、13 章风险表、8.1 SLO 前提说明） |
| 周期 | T+0 ~ T+6 周，按 2 人基线排期 |

## 1. 目标

M0 不交付产品功能，只回答两个问题和建一套设施：

1. **能跑通**：Firecracker 冷路径端到端打通——boot → vsock → guest 内 exec → 销毁无残留。
2. **有数字**：冷启动延迟与密度的实测基线，验证 PRD 的 SLO 前提是否成立。
3. **设施**：基准 CI（每 PR 跑），它是后续所有里程碑的性能回归防线（13 章风险表硬性要求）。

出口标准（PRD）：单节点 demo，`run` 一个命令端到端 ≤1.5s；基准 CI 在 PR 上可跑、有数。

## 2. 要回答的验证问题（风险清退清单）

| # | 问题 | 验证方式 | 通过判据 |
| --- | --- | --- | --- |
| Q1 | FC boot + sl-envd init + exec 链路能否打通 | 端到端 demo | `run` 返回 stdout + 退出码 |
| Q2 | sl-envd 作为 PID 1 是否可行（ADR-18） | 僵尸回收压力测试（fork bomb 级进程树后检查 PID 泄漏） | 无 zombie 累积、无 PID 耗尽 |
| Q3 | 冷路径 ≤1.5s 是否可达，耗时分布在哪 | 分段计时（见 §5） | P99 ≤1.5s，各段有分解数据 |
| Q4 | 密度基线：64C/128G 单机实际能跑多少实例 | 并行 boot N 实例至 OOM/降级 | 给出实测曲线（CPU/内存/实例数） |
| Q5 | 自带精简内核构建管线是否可走通 | 内核构建脚本 + 可复现构建 | 一键产出内核镜像，记录构建时长 |
| Q6 | 资源销毁是否真无残留（FR-1.3 雏形） | 反复 create/destroy 后对账 | 无进程/netns/tap/磁盘残留 |

Q4 的实测直接服务 8.1 密度说明中"M0 基准 CI 增加密度实测项、M2 复审"的承诺。

## 3. 范围与非范围

**范围内**：

- FC 后端驱动原型（Rust 二进制，直接调 Firecracker API，不经任何编排层）
- 自带精简内核构建管线（脚本化，Firecracker 推荐配置裁剪）
- 基础 rootfs 制作（busybox 级 + sl-envd 静态二进制）
- sl-envd 原型：PID 1 职责（挂载 proc/sysfs/dev、僵尸回收）+ vsock 服务 + 同步 exec（stdout/stderr/退出码）
- netns + tap 建立与拆除（纳入冷路径计时；无任何放行规则，结构性 deny 天然成立，ADR-13）
- 基准 CI（GitHub Actions 裸金属 runner 或自建 runner，见 §5）

**范围外**（明确不做，碰了就是范围蔓延）：

- 快照/恢复、预烘焙、预热池（M1 内部引擎，决策 16）——因此 dm thin pool 也不进 M0，demo 用只读共享 base rootfs + tmpfs 写层
- 模板系统、API Server、SDK、CLI 正式版（demo 用节点原型二进制的子命令即可）
- 白名单/DNS/网关等一切网络策略（M1+）
- 信号转发、PTY、文件 API（M1/M2）
- dm-thin、快照加密、etcd——全部 M1 以后

## 4. 技术要点与既定约束

- **sl-envd 是 PID 1**（ADR-18）：M0 就要按这个形态做，不允许"先拿 bash 当 init 顶着"——Q2 的验证就是为此。
- **vsock 通信**（ADR-4）：host 端通过 AF_VSOCK 直连 guest sl-envd，协议用最小的长度前缀帧 + protobuf（或先 JSON，M1 定契约）。guest CID 分配策略从 M0 就记录（500 实例/节点的 CID 空间管理是 M2 网关多路复用的基础）。
- **网络只做建立/拆除**：netns + tap + 无放行规则。不装 NAT，出口天然为零。
- **rootfs 方案 M0 特化**：共享只读 base + tmpfs 写层，不引入 dm-thin（ADR-23 的完整存储栈随 M1 快照引擎一起落地）。密度测试据此标注"无 per-实例磁盘层"的口径。
- **内核**：x86_64，FC 推荐配置裁剪，≥5.18（ADR-12 的 vmgenid 前提从内核版本开始守）。

## 5. 基准 CI 设计

**指标**（每 PR 跑，结果入库可对比）：

| 指标 | 口径 | M0 参考线 |
| --- | --- | --- |
| 冷启动端到端 | `run` 发起 → stdout 返回，P50/P99 | ≤1.5s（P99，出口标准） |
| 冷启动分段 | FC boot / rootfs 挂载 / netns+tap / vsock 建连 / envd ready / exec 各段耗时 | 有分解数据即可 |
| 密度 | 并行实例数 vs 内存/CPU 曲线，至失败点 | 有实测曲线 |
| 销毁残留 | N 轮 create/destroy 后资源对账 | 0 残留 |

**运行环境（分层，W1 决策）**：KVM 是唯一硬要求，CPU/内存只影响可测规模。日常开发与轻量基准（冷启动/销毁对账）用 GitHub 托管 runner（ubuntu-latest 自带 /dev/kvm，4C/16G）或任意 KVM 开发机；**密度实测**才需要 64C/128G（与 8.1 密度声明同规格，数据才可比），按次租用裸金属、手动 dispatch `bench-density` job 执行，不做常态持有。规避无嵌套虚拟化的常规云实例（AWS 仅 .metal；GCP 需显式开启 nested virt；Azure Dv3+ 默认开启）。

**page cache 冷/热两档**：测量脚手架按 8.1 SLO 前提说明预留（M1 快照引擎落地后直接复用）。

## 6. 周计划（2 人基线）

| 周 | 内容 | 交付 |
| --- | --- | --- |
| W1 | 裸金属 runner + CI 骨架；FC 开发环境；内核构建脚本初版 | runner 可用；内核镜像 v0 |
| W2 | 最小 rootfs + sl-envd 骨架（PID 1、挂载、vsock echo） | VM 内 envd 可与宿主通信 |
| W3 | exec 链路（host→vsock→envd→spawn→stdout/退出码回传） | demo 首次端到端跑通 |
| W4 | netns/tap 接入创建路径；销毁对账逻辑；分段计时埋点 | Q1/Q6 通过 |
| W5 | 基准 CI 成型（冷启动分段 + 销毁对账进 CI）；僵尸回收压测 | Q2/Q3 通过；CI 每 PR 跑 |
| W6 | 密度实测与曲线；出口评审；内核跟进策略文档（14.2-2 闭环） | Q4/Q5 通过；M0 出口评审 |

缓冲说明：W3 是全计划最大不确定点（vsock 与 init 细节的第一次合龙），若滑期，W5/W6 的密度实测可压缩为一档，但**基准 CI 骨架不可让位**——它是 M1 的开工前提。

## 7. 风险与回退

| 风险 | 应对 |
| --- | --- |
| 裸金属 runner 不可得（只有无嵌套虚拟化的云实例） | 已分层（§5）：轻量基准走托管 runner；密度实测按需租用。剩余风险仅为 W6 密度 campaign 前的租用落实 |
| sl-envd init 职责超预期（僵尸回收边界 case） | 缩小 Q2 判据到"常规进程树"，极端 case 记录为 M1 issue，不阻塞出口 |
| 冷启动 >1.5s | 分段数据定位大头；rootfs 体积与内核裁剪是首要嫌疑；出口评审凭分段数据决策，不接受无数据的说法 |
| 2 人被社区/杂务分流 | M0 期间不做任何对外发布与社区运营，仓库私有或静默公开 |
