## 2. 延迟四行：数字很宽裕，但有两处要说明

分位全部大幅优于口径（创建 P50 23ms vs 100ms，冷启动 P99 405ms vs 1500ms）。两点需要在
出口评审时讲清楚，否则会被过度解读：

**① 快照恢复 P50 = 1ms 不代表「沙箱已可用」。** `load_p50=1, resume_p50=0`——Firecracker 的
`snapshot/load` 用 File 内存后端是 **lazy mmap**，API 立刻返回，页错误在之后按需发生。1ms 是
真实的 API 耗时，但整条「创建走恢复路径」是 `restore_create.p50_ms = 25ms`，那才是用户可感的数。
两个数都远低于 200ms 口径，结论不变，但引用时要说清是哪一个。

**② 温池在这台机器上没有产生收益。** `cold_p50=23, warm_p50=23, copy_saved_p50=0`——因为
XFS reflink 让 rootfs 拷贝本身就 ≈0ms（`restore_create.copy_p50 = 0`），池要省的那一段本来
就不存在了。**这反过来证明 XFS 那步做对了**：在 ext4 上这里会是全量拷贝，池才有意义。
换言之「池命中 P50」这一行在本次实测里等价于「恢复路径本身有多快」。

## 3. 密度两行：门线达到了，但证据不支持字面解读

**这一节是本记录最重要的部分。** 数字是 PASS，但如果按字面理解会得出错误的部署结论。

### 3.1 两趟都是撞参数上限，不是真实天花板

```json
{"spec":"default","max_instances":400,"stop_reason":"reached-max","per_vm_mb_est":19,
 "mem_start_mb":123912,"used_total_mb":7987}
{"spec":"micro",  "max_instances":900,"stop_reason":"reached-max","per_vm_mb_est":7,
 "mem_start_mb":123707,"used_total_mb":6396}
```

`stop_reason` 都是 **`reached-max`**——撞的是本次设的 `DENSITY_MAX`（400 / 900），**不是内存
地板**。所以「400」「900」就是那两个参数本身，真实上限只知道「比这更高」，**未探到**。

### 3.2 内存只用了总量的 5–6%，因为实例是空闲的

均摊 **19MB/实例（配置 512MiB）**、**7MB/实例（配置 128MiB）**——Firecracker 的 guest 内存走
**惰性缺页**，空闲实例从未触碰过自己那份 RAM，物理页就没落下来。

PRD §8.1 的脚注恰好预判了这件事：

> 同模板恢复的多个沙箱可通过共享快照文件 page cache + 懒加载（脏页率低时）提升实际密度，
> 但该收益取决于同模板占比与脏页率两个变量，**不作为 SLO 承诺**。

### 3.3 因此，这份证据支持什么、不支持什么

| 支持 | 不支持 |
| --- | --- |
| 「400 个空闲的 2c/512M 实例可共存，共用约 8GB」 | 「200 个**真实负载**各吃 512MiB 仍可共存」 |
| 「900 个空闲的 micro 实例可共存，共用约 6.4GB」 | 「500 个**真实负载**各吃 128MiB 仍可共存」 |
| 密度门线（≥200 / ≥500）在空闲态下达到 | 密度天花板的具体数值（未探到） |

**按 §8.1 的字面判据（≥200 / ≥500）——达标。** 但把这个数字当容量规划依据会 OOM。

### 3.4 待办

1. **补探真实上限**：抬高 `DENSITY_MAX` 重跑到 `stop_reason` 变成 `mem-floor` 或启动失败。
   本次因租机时间未做（当时判断现有数据已足够 M3-Q9 达标）。
2. **让密度基准施加真实内存压力**：现有 `bench-density.sh` 起的是空闲实例。要让密度数字能
   当容量规划依据，需要在实例内触碰一定比例的 guest 内存（脏页率可配）。这是基准设计变更，
   单列跟进。
3. `slo-gate.sh` 已把这两条限定**印进判定表**（`下界·未探到上限`、`空闲实例(均摊N M«配置M M)`），
   使后来者不会只看到一个光秃秃的 PASS。

## 4. 过程中修掉的两个真 bug

都是只有真机跑起来才会暴露的：

1. **`build-rootfs.sh` 把 static-pie 误判为动态链接**（`8ce6691`）。Rust 的 musl target 产出
   static-pie（无 PT_INTERP，自包含），而 Ubuntu 20.04 的 `file 5.38` 早于 static-pie 支持、
   把它描述成 "dynamically linked"，旧判据正好 grep 这个词——于是**在它本该放行的二进制上报错**。
   判据已改为 `readelf` 查 PT_INTERP 段。任何 `file < 5.39` 的发行版都会踩到。
2. **密度基准的规格错配**（`04f2727`，租机前发现）。`sl-node run` 曾把 machine-config 写死
   `1 vCPU/128MiB`，于是密度量的是 micro 档却按默认档 gate。若未修复，本次会拿到一份
   「密度 400 台 @ 默认规格 PASS」的报告，而实际测的是 128MiB 实例——数字对、结论错、看不出来。
