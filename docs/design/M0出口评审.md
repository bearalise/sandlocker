## 1. 验证问题结论（§2 风险清退）

| # | 问题 | 结论 | 证据 |
| --- | --- | --- | --- |
| **Q1** | FC boot + sl-envd init + exec 链路能否打通 | ✅ 通过 | W3 demo：`uname -a` 见 guest 内核 6.6.147、stdout 回传、`exit 7` 退出码精确传播、`ls 不存在路径` stderr 分离且 exit=1 |
| **Q2** | sl-envd 作为 PID 1 僵尸回收是否可行 | ✅ 通过 | `bench-reaper`：guest 内 300–500 fork 风暴（含孤儿 reparent 到 PID1）后 **0 僵尸**；收割状态表有界化（FIFO 上限）防孤儿状态无界堆积 |
| **Q3** | 冷路径 ≤1.5s 是否可达、耗时分布 | ✅ 通过 | `bench-coldstart`：**P50=554ms / P99=565ms**（远低于 1.5s 出口线）；分段 pre-kernel(host: unshare/tap/FC 加载) ~290ms + guest boot→ready ~260ms |

| **Q5** | 自带精简内核构建管线是否走通 | ✅ 通过 | `build-kernel.sh` 一键产出未压缩 ELF `vmlinux-6.6.147`；FC 基线+fragment 逐项生效校验 + ELF 断言；`validate` job 每 PR 验证可构建性 |
| **Q6** | 资源销毁是否真无残留 | ✅ 通过 | `bench-teardown` N 轮 create/destroy + 密度探针收尾：**0 残留**（firecracker 进程 / host tap / vsock socket）；killpg 整组回收 + netns 随进程自动清理 |

## 3. M1 开工条件（分段数据作为快照引擎设计输入）

M0 的冷路径分段直接指向 M1 快照引擎的收益空间：

- **总冷启动 ~555ms**拆为两半：pre-kernel ~290ms（unshare/tap/FC 进程与内核加载）+ guest boot ~260ms。
- 快照恢复（M1）跳过 guest boot 全过程 + 内核加载，目标 P50 ≤200ms（FR-1.4）——分段数据表明"guest boot ~260ms + 内核加载"正是快照要省掉的部分，收益空间与 SLO 目标自洽。
- 温池/热池（ADR-23）针对的 page cache 冷/热差异，其测量脚手架已在 bench 预留（热档待快照池落地复用）。

## 5. 已知局限（诚实记录，移交 M1）

- **无快照/预烘焙/预热池**（M1 内部引擎，ADR-6/23）：故 exec 为同步、无流式；stdout/stderr 走 UTF-8 有损转换（二进制精确留 M1）。
- **网络为 rootless netns 原型**：仅 build/teardown + 结构性 deny（无 allow 条目）；命名 netns + nftables 白名单 / DNS 劫持是 M1（FR-3.2/ADR-20/21）。
- **单沙箱共享 rootfs**：无 per-实例磁盘层（dm-thin 是 M1，ADR-23）；密度对账不含磁盘层残留检查（符合计划 §4 口径）。
- **Q4 真实密度数据未产**：受限于开发机 7G 内存；脚本与方法学已验证，须裸金属 dispatch 补 64C/128G 数据。
- **CI 冷/热两档的热档**：脚手架预留，待 M1 快照池落地。
- **GitHub Actions 上 bench-light 未经真实 PR 验证**：托管 runner 的 `/dev/kvm` + unshare userns 组合本机已验证，首个 PR 应实证。
