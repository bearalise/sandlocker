# SandLocker 部署指南

把仓库 clone 到一个全新环境后，如何从零跑通。本文覆盖依赖安装、运行时工件构建、环境自检、运行方式，以及新环境最常踩的坑。

> 适用范围：单机开发 / 自部署起步（PRD §"自部署一等公民"）。当前里程碑 M1，架构为 Rust workspace + Firecracker microVM 后端。

---

## 0. 硬性前提

- **架构**：仅 x86_64（`fetch-firecracker.sh` / rootfs 均硬编码 `x86_64`）。
- **KVM**：起 microVM 必须 `/dev/kvm` 可写 —— 裸金属，或开启了嵌套虚拟化的 VM / WSL2。
  没有 KVM 仍可做：工作区编译、单元测试、guest 内核构建；但 demo / 生命周期 / 基准跑不了。
- **非特权 user namespace**：本项目网络与私有 rootfs 走 rootless（`unshare --map-root-user`），
  需要内核允许非特权 userns。见 §5 常见问题（Ubuntu 24.04 默认拦这个）。

`build/` 与 `target/` 都在 `.gitignore` 里 —— **clone 后 `build/` 是空的，运行时工件必须自己生成**（§2）。

## 1. 安装依赖

### 1.1 系统包

```bash
sudo apt-get update && sudo apt-get install -y \
  build-essential flex bison libelf-dev libssl-dev bc \
  e2fsprogs nftables iproute2 curl
```

| 包 | 用途 |
|---|---|
| `build-essential flex bison libelf-dev libssl-dev bc` | 构建 guest 内核（`scripts/build-kernel.sh`） |
| `e2fsprogs`（`mke2fs`） | 免 sudo 造 ext4 rootfs（`scripts/build-rootfs.sh`） |
| `nftables iproute2` | 网络后端 / netns / tap |
| `curl` | 拉 Firecracker、内核源码 |

### 1.2 Rust 工具链（含 musl target）

`sl-envd` 是 guest 里的 PID 1，要求 musl 静态链接，故必须额外装 `x86_64-unknown-linux-musl`。

```bash
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
. "$HOME/.cargo/env"                        # 让当前 shell 立即能用 cargo
rustup target add x86_64-unknown-linux-musl
```

验证：

```bash
cargo --version
rustup target list --installed | grep musl   # 应有 x86_64-unknown-linux-musl
```

> 项目无 `rust-toolchain.toml`，用 stable 即可（与 CI 的 `dtolnay/rust-toolchain@stable` 一致）。

**国内镜像（可选）**

- rustup（工具链下载），装 rustup **之前** export，建议写进 `~/.bashrc`：

  ```bash
  export RUSTUP_DIST_SERVER="https://mirrors.tuna.tsinghua.edu.cn/rustup"
  export RUSTUP_UPDATE_ROOT="https://mirrors.tuna.tsinghua.edu.cn/rustup/rustup"
  ```

- cargo（拉 crates），写入 `~/.cargo/config.toml`：

  ```toml
  [source.crates-io]
  replace-with = 'tuna'
  [source.tuna]
  registry = "sparse+https://mirrors.tuna.tsinghua.edu.cn/crates.io-index/"
  ```

## 2. 生成运行时工件

这两样是 microVM 的硬依赖，且被 gitignore，clone 后必须自己生成。

### 2.1 Firecracker 二进制

```bash
scripts/fetch-firecracker.sh            # 默认 latest；也可 scripts/fetch-firecracker.sh v1.16.1
```

产物：`build/firecracker/firecracker`、`build/firecracker/jailer`。
需能访问 GitHub；受限网络可手动下载对应 `firecracker-<版本>-x86_64.tgz`，解压后把两个二进制放进 `build/firecracker/` 并 `chmod +x`。

### 2.2 Guest 内核

```bash
scripts/build-kernel.sh                  # 默认 6.6
```

产物：`build/kernel/vmlinux-<版本>` + 软链 `build/kernel/vmlinux` + `.sha256` + `build-info.txt`。

- 以 Firecracker 官方 guest config（6.1 基线）为起点，叠加 `scripts/kernel-fragment.config`
  （vmgenid / vsock / dm-thin 等必需项），`olddefconfig` 适配后编译。
- **耗时最长**（几分钟到十几分钟，取决于核数）；**不需要 KVM**。
- 系统缺 `flex/bison/m4`/libelf 头时会回退到仓库内 `.toolchain/`（若存在）。

## 4. 运行

先把工作区编出来：

```bash
. "$HOME/.cargo/env"
cargo build --release -p sl-node
cargo build --release -p sandlocker
cargo build --release -p sl-envd --target x86_64-unknown-linux-musl
```

### 路径 A：端到端 demo（先验通链路，最省事）

```bash
scripts/run-demo.sh
```

自动：编 `sl-node` → 编 `sl-envd`(musl) → 造 rootfs → 起 microVM 做 host↔guest vsock echo。
**要 KVM + userns**。看到 `W4 demo PASS` 即整条链路 OK。

### 路径 B：用户面 CLI（`sandlocker`，纯 REST 客户端）

```bash
# 1) 起守护（前台，默认 127.0.0.1:7878）；实为 sl-node --serve
./target/release/sandlocker up

# 2) 另开终端
./target/release/sandlocker build examples/hello.sandlocker.toml
./target/release/sandlocker run <template>
./target/release/sandlocker ps
./target/release/sandlocker exec <id> -- <cmd>
./target/release/sandlocker logs <id>
./target/release/sandlocker snapshot <id>
```

> `sandlocker` 的 `up`/`build` 会转发到**同目录的兄弟 `sl-node` 二进制**，两者需在同一 `target/release/`。
> 契约见 `contracts/openapi.yaml`。

### 路径 D：Python SDK（`sandlocker` 包，纯 stdlib）

给终端用户的编程接口（PRD 7.6）。零第三方依赖，契约见 `contracts/openapi.yaml`，详见 `sdk/python/README.md`。

```bash
# 1) 起守护 + 备一个模板
./target/release/sandlocker up &                             # 默认 127.0.0.1:7878
./target/release/sandlocker build examples/hello.sandlocker.toml

# 2) 装 SDK（或免安装用 PYTHONPATH）
pip install -e sdk/python          # 方式一
export PYTHONPATH="$PWD/sdk/python/src"   # 方式二（免安装）

# 3) 三行手感
python3 - <<'PY'
from sandlocker import Sandbox
with Sandbox.create(template="hello", timeout=300) as sbx:
    print(sbx.run("echo hi").stdout, end="")
PY

# 4) 或跑用户故事场景（US-1/US-4/US-7）
export SANDLOCKER_ADDR=127.0.0.1:7878
python3 examples/sdk/us1_quickstart.py    # 创建→跑分析→取产物→空闲自动销毁
python3 examples/sdk/us4_template.py      # 团队模板 + 秒级就绪
python3 examples/sdk/us7_ci_ephemeral.py  # CI 跑不可信测试，退出码透传 + 跑完即焚
```

> **M1 边界**：基座 rootfs 是 busybox（**无 Python 解释器**），且模板构建 deny 网络（无法 pip）。
> 故示例用 busybox shell 命令演示；真正的「Python + pandas」团队模板需 M2 的 allow-network 构建。详见 `sdk/python/README.md`。

一键门禁（自动起守护、跑三场景、断言零残留；KVM/python3 缺失则跳过退 0）：`scripts/verify-sdk-e2e.sh`。

### 路径 C：底层 `sl-node` 直接对账（CI 用的回归命令）

默认路径已内置（`build/kernel/vmlinux`、`build/rootfs/rootfs.ext4`、`build/firecracker/firecracker`）。

```bash
# 模板构建（rootless，deny 网络离线，无需 root）
./target/release/sl-node --build examples/hello.sandlocker.toml --json

# 生命周期对账（要 KVM）；先 --build 拿 <version>
./target/release/sl-node --orch-reconcile build/templates/hello/<version> --json

# 存储 / 网络对账（要 root）
sudo ./target/release/sl-node --dmthin-reconcile --cycles 5 --json
sudo ./target/release/sl-node --nftfw-reconcile --json
```

常用参数（`parse_args`）：`--kernel/--rootfs/--fc/--jailer/--workdir` 覆盖路径，
`--boot api|config-file|jailer`、`--no-netns`、`--json`、`--cycles N`、`--hold-secs N`。

### 无 KVM 环境能做什么（等价 CI 的 `validate` job）

```bash
for f in scripts/*.sh scripts/bench/*.sh; do bash -n "$f"; done   # 脚本语法检查
cargo build --workspace --release
cargo test -p sl-proto -p sl-node -p sl-store -p sandlocker        # Rust 单元测试
python3 -m unittest discover -s sdk/python/tests                    # Python SDK 单测（假 daemon）
scripts/build-kernel.sh                                             # 内核构建不需 KVM
```

## 4.5 集群部署：独立数据面网关（M3 W5，ADR-22）

单机不需要这一节——`sl-node --serve` 自带进程内网关，行为与 M2 一致。**集群**（`--serve --etcd`）
才需要把数据面网关拆成独立进程，因为「API 请求落到副本 X、沙箱却在节点 Y」时需要有人把字节转过去。

连接方向恒为 **节点 → 网关**：节点预拨若干条持久连接停在网关上、供网关反向借用。
因此**节点不需要开放任何入站端口**，可以待在防火墙/NAT 后面。

```bash
# ① 造证书（生产请用你自己的 CA / cert-manager；SAN 必须与 --gw-tls-name 一致）
openssl req -x509 -newkey rsa:2048 -nodes -days 365 -subj "/CN=sandlocker-ca" \
  -keyout ca.key -out ca.pem
# 分别为网关（SAN=sandlocker-gw）与各节点签一张，EKU 需含 serverAuth,clientAuth

# ② 起网关（可多副本，前面挂 L4 LB；网关不持沙箱状态，任一副本服务任一沙箱）
sandlocker-gw --bind 0.0.0.0:7879 --node-bind 0.0.0.0:7880 \
  --etcd http://etcd:2379 \
  --tls-cert gw.pem --tls-key gw.key --tls-ca ca.pem

# ③ 起节点（--gw = 网关的节点接入口；--gw-url = 网关面向客户端的基址，签名 URL 指向它）
sl-node --serve --etcd http://etcd:2379 \
  --gw gw-lb:7880 --gw-url http://gw-lb:7879 \
  --gw-tls-cert node.pem --gw-tls-key node.key --gw-tls-ca ca.pem \
  --gw-tls-name sandlocker-gw
```

要点：

- 二进制须以 **`--features cluster`** 构建（`cargo build --release -p sl-node --features cluster`），
  否则 `--etcd` / `sandlocker-gw` 会直接报错退出。
- **默认不放行明文**：漏配证书会报错而不是静默降级成无鉴权传输。本机对账/开发可显式加
  `--gw-insecure`（两端都要加），**不要用于生产**。
- `--gw-pool`（默认 8）是节点维持的**空闲**连接数，不是并发上限；并发上限是 `--gw-max-streams`
  （默认 256）。空闲池会在开流的瞬间补回，所以长连接（PTY）不会把余量占死。
- 自检：`sl-node --gw-dataplane-reconcile --etcd <ep> --gw-tls-cert ... --gw-tls-key ... --gw-tls-ca ...`
  会起一套真网关 + 两个真节点代理跑完整断言；`scripts/verify-gw-dataplane.sh <etcd-ep>` 连证书一起造。

**跨节点覆盖面（M3 W4 余项补齐后）**：数据面（exec / logs / 文件 / 端口 / 流式 exec）与
**控制面**（pause / resume / fork / destroy / keepalive / expose / unexpose / exposes）都会自动
转到沙箱所在节点。**打哪个副本都一样**——不需要客户端先查沙箱在哪台机器上。

只读且纯 store 的路由（`GET /v1/sandboxes`、单沙箱 meta、审计、模板）本来就任一副本自足，
不走中继。

**放置（M3 调度器）**：`POST /v1/sandboxes` 打到哪个副本都行——副本会**盘点存活节点**、
挑一个放得下的建，选中别人就把创建整个转过去（同一条反向隧道）。

- 口径：**剩余内存最多者优先**；vCPU 只作准入。依据是 M3-Q9 的裸金属实测——密度的停因始终
  是内存，CPU 从不是先触顶的那一维。
- 容量按沙箱的**配置内存**记账，不按实测占用。Firecracker 惰性缺页让空闲实例只落很少物理页
  （实测 512MiB 的实例约 19MB），但 PRD §8.1 脚注写明这份收益**不作为 SLO 承诺**。要吃它请
  显式 `--sched-overcommit <n>`，并自担 OOM 风险。
- 节点容量随心跳上报（`node/<id>` 键）。**没上报容量的节点不会被选中**——读不到容量不等于
  容量无限。滚动升级时旧版本节点会暂时退出候选，升完自动回来。
- **不配 `--gw-url` 就没有放置**（调度器要靠那条通道把创建转走），行为退回「谁收到就谁建」。
- 放不下（所有节点都满）→ 在本节点建；本节点也放不下则照常报错。调度是优化，不是新的故障源。

两处要知道：

- **暴露的地址在 owning 节点上**。`POST /v1/sandboxes/{id}/expose` 转到 owning 节点后，监听器
  起在**那台机器**上，返回的 `host_port` 也是那台机器的端口。默认 `bind=127.0.0.1` 时只有该
  节点自己可达；要给外部访问，需 `--expose-allow-public` + 显式 `bind` 到节点的可路由地址
  （见 `docs/design/端口暴露.md` 的安全说明）。
- **控制面 ticket 不签发给客户端**。`POST /v1/sandboxes/{id}/ticket` 只签数据面动作
  （exec/file/logs/port/stream）；请求 `action=pause` 一类会被拒。控制面票只由副本在转发时
  自签、一次性、且**操作名进签名**——所以一张 pause 票改不成 destroy 票。生命周期操作请走
  对应 `/v1` 端点，那条路上才有配额前置检查（FR-7.2）与审计落账（FR-7.3）。

## 4.6 快照加密（M3 W9，ADR-15）

暂停态快照就是一份**完整的 guest 内存镜像**，里面有当时进程持有的一切——盘被拷走等于凭据被拷走。
开启后，`pause` 落盘的 `vmstate`/`mem` 会被封成 `.enc`（AES-256-GCM，4MiB 分块），明文当场抹除。

```bash
# ① 生成根密钥（0600）。拒绝覆盖既有文件——覆盖 = 所有既有快照永久不可解。
sl-node --snap-kms-init /etc/sandlocker/root.key

# ② 起守护时带上它（不带 = 不加密，快照明文落盘，即 M2 行为）
sl-node --serve --snap-kms-key /etc/sandlocker/root.key ...
```

**先把这几件事想清楚再开：**

- **根密钥丢失 = 所有暂停态快照永久不可解**，没有后门也没有恢复流程。请像对待备份加密密钥一样
  备份它（离机保存），并纳入你的密钥轮换流程。
- **加密改变快照落盘格式**，与既有明文快照不兼容。开启前先把在跑的沙箱 resume 掉或销毁掉。
- **护到哪一步**：护的是**暂停态**快照——节点关机后仍在盘上的那份。运行中实例的 `mem` 必须是
  明文（Firecracker 全程 mmap 它），这不构成额外暴露：运行中的内存本来就在宿主 RAM 里。
- **不护什么**（PRD §8.2 威胁模型，务必如实理解）：
  - V1 是**文件 KMS（开发级）**，根密钥就在节点上 → **防盘被整体拷走，不防节点被攻破**。
    Vault KMS 插件列 P1/GA。
  - **`pause` 会捕获 guest 内存中当时存在的一切 secret**。sl-envd 会在 pause 前擦掉**自己的**
    会话密钥，但管不了用户进程持有的凭据——用户侧的密钥轮换要由你的应用负责。
  - 抹除是「覆写再 unlink」。在 CoW/日志式文件系统（btrfs、ext4 data=journal）与 SSD FTL 之下
    **不保证**原物理块被真正擦掉；这是纵深防御，真正的保证来自明文只在加解密前后短暂存在。
- 自检：`sl-node --snapcrypt-reconcile [--etcd <ep>]`（往返 / 篡改即拒 / 明文不落盘 / 租户隔离 /
  分块随机读，共 9 条）。

**密钥层级**：根密钥（KMS）→ 租户 KEK（每项目一把，**以密文**存控制面 `kek/<project>`）→
快照 DEK（每快照一把，**以密文**存快照头）。节点不持久化任何明文密钥。

## 4.7 多租户鉴权 + 配额（M3 W6/W7，FR-7.1/7.2/7.3）

模型：**组织 → 项目 → API Key（作用域）**。签发在服务端由运维方用 CLI 完成，应用只**消费** token
（无自助/程序化签发——图形化 Key 管理属控制台完整操作面，留 GA）。守护带 `--require-auth` 才校验。

### ① 签发 API Key（运维方，token 明文仅显示一次）

```bash
# 对准守护所用的同一 store：单机 --store <sqlite>，集群 --etcd <ep>（后者需 --features cluster 构建）
sl-node --apikey-create --org acme --project team-a --scope readwrite --store build/templates/sl.db
# 输出： token=9f2c1a59fb6bd02e...   ← 这就是 SANDLOCKER_API_KEY
```

- 作用域三档：`readonly`（只读）/ `readwrite`（读写）/ `build`（含构建）；层级 Build ⊇ ReadWrite ⊇ ReadOnly。
- store 只存 `apikey/<sha256(token)>` → 记录（org/project/scope），**不存明文**——泄露 store 不泄露可用 token；
  token 丢失只能重签。

### ② 设项目配额（可选，按项目）

```bash
sl-node --quota-set --project team-a \
        --max-sandboxes 20 --max-vcpus 40 --max-mem 40960 --max-storage 20480 \
        --store build/templates/sl.db      # 0 = 该维度不限
```

超限 → `QUOTA_EXCEEDED`（HTTP 429，create/fork/pause 前置检查）。用量按项目实时累计。

### ③ 起守护（开鉴权门）

```bash
sl-node --serve --require-auth --store build/templates/sl.db   # 集群加 --etcd <ep>
```

- 每个 `/v1` 请求须带 `Authorization: Bearer <token>` 或 `X-API-Key: <token>`；缺/错 → 401，
  作用域不足 / 跨项目 → 403，配额超限 → 429。
- `GET /metrics` 与 `/gw/*` 数据面（ticket 自带鉴权）**不**走 API Key 门。

### ④ 应用消费（SDK / CLI / curl）

```bash
export SANDLOCKER_API_KEY=9f2c1a59fb6bd02e...     # 注入 K8s Secret / CI secret / .env
```

```ts
// TS SDK ≥0.5.0：自动读环境变量，每请求带 Authorization
const sbx = await Sandbox.create("hello");
// 或显式：Sandbox.create("hello", { apiKey: "..." })
```
```python
# Python SDK ≥0.2.0
from sandlocker import Sandbox
sbx = Sandbox.create("hello", api_key="...")     # 或设 SANDLOCKER_API_KEY
```
```bash
curl -H "Authorization: Bearer $SANDLOCKER_API_KEY" http://<daemon>/v1/sandboxes
```

SDK 把 401/403/429 映射为 `Unauthorized`/`Forbidden`/`QuotaExceeded`（均 `ApiError` 子类）；
`client.audit()` 读按项目过滤的审计日志（`GET /v1/audit`，append-only，FR-7.3）。

### 典型 onboarding 流（每个试用团队一遍）

1. `--apikey-create --org <org> --project <team> --scope <scope>` 签一把（选合适作用域）。
2. `--quota-set --project <team> --max-*` 给该项目配额。
3. 把 token 塞进该团队应用的密钥托管（K8s Secret / CI secret）。
4. 沙箱按项目隔离：一把 key 只看得见 / 操作得了自己项目的沙箱。

自检：`sl-node --auth-reconcile [--etcd]`（有效/无效/越权/项目隔离）、
`sl-node --quota-reconcile [--etcd]`（超限拒 / 删后可建 / 项目隔离 / 审计 append）。

## 4.8 可观测性（M3 W8，§7.8）

三件事各走各的口子，互不依赖，都**默认关闭或零成本**：

| | 怎么开 | 出什么 |
| --- | --- | --- |
| 指标 | 恒开（免鉴权） | `GET /metrics`，Prometheus 文本格式。分位由 Prometheus 端 `histogram_quantile()` 算 |
| 结构化日志 | `--log-sink <url>` | 生命周期事件 JSON POST 到外部收集器（Loki/ES/自建） |
| **分布式追踪** | `--otlp-endpoint <url>` | OTLP/HTTP-JSON POST 到 Collector 的 `/v1/traces` |

```bash
sl-node --serve --etcd http://etcd:2379 \
  --gw gw:7880 --gw-url http://gw:7879 --gw-tls-* ... \
  --otlp-endpoint http://collector:4318          # 写全 .../v1/traces 也接受
```

**一次创建是一条完整链路**（M3-Q5 判据）：

```
POST /v1/sandboxes                (副本 X，SERVER)
├─ schedule                       候选几台 / 选了谁 / 为什么
├─ relay.create                   跨节点那一跳（CLIENT）
│  └─ node.create                 ← 在**节点 Y** 上，靠 traceparent 接上
│     ├─ rootfs.copy
│     ├─ vmm.api_ready
│     ├─ snapshot.load
│     └─ vm.resume
```

- 客户端带 `traceparent` 头（W3C）就**接着你那条 trace 画**，于是"用户点一次按钮"到
  "guest 起来了"是同一条链路；不带就自成一条。格式不合规的头一律忽略并另起一条——
  半个 id 拼进去会产出一条永远对不上的链路，比没有更难查。
- `rootfs.copy` 等四个分段是**由实测时长推算出的时刻**（`CreateOutcome` 只量了时长），
  按恢复路径的真实顺序铺开；span 上带 `sandlocker.segment_from_duration=true` 标着这件事。
- 导出是 **best-effort**：有界队列 + 后台线程批量发，队列满或 Collector 不可达就丢。
  **丢了看得见**——`sandlocker_otlp_spans_dropped_total` 在 `/metrics` 上。遥测拖垮沙箱是
  本末倒置，但静默丢弃会让人把"缺了一段"读成"那一步没发生"。
- 实现是**手写**的 OTLP/HTTP-JSON（`crates/sl-node/src/trace.rs`）：官方 OTel Rust SDK 拖
  tokio 异步栈，而本项目从 M1 起全同步（ADR-3/D2 异步隔离区）。**零新增依赖**——
  ureq 与 serde_json 早在依赖树里。

自检：`sl-node --otlp-reconcile`（起一个真 HTTP 收集器，画一条跨节点创建形状的链路，
收下真载荷验：同一 traceId / 跨进程父子接得上 / 纳秒为字符串 / ERROR 状态 / 零丢弃）。

## 5. 常见问题（FAQ）

排障总入口：microVM 相关失败先看 **`build/run/console.log`**（FC 的 stdout/stderr + guest 串口 + sl-envd 日志）。

### 5.1 `unshare: 写失败：/proc/self/uid_map: 不允许的操作`

**现象**：`run-demo.sh` 报 `FC 在 API 就绪前退出（status=1）`，console.log 首行是上面这句。
**根因**：本项目网络/私有 rootfs 走 rootless（`unshare --net --map-root-user`），而内核禁用了非特权 user namespace。

先定位是哪种禁用：

```bash
sysctl kernel.unprivileged_userns_clone            # 应为 1
sysctl kernel.apparmor_restrict_unprivileged_userns # Ubuntu 24.04 默认 1 → 就是它
sysctl user.max_user_namespaces                    # 应 > 0
unshare --user --map-root-user true && echo OK || echo BLOCKED   # 自测
```

对应修复：

| 查到 | 修复 |
|---|---|
| `apparmor_restrict_unprivileged_userns = 1`（Ubuntu 23.10+/24.04 最常见） | `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0` |
| `unprivileged_userns_clone = 0`（Debian/老 Ubuntu） | `sudo sysctl -w kernel.unprivileged_userns_clone=1` |
| `user.max_user_namespaces = 0` | `sudo sysctl -w user.max_user_namespaces=15000` |

永久生效（示例 apparmor 那条）：

```bash
echo 'kernel.apparmor_restrict_unprivileged_userns=0' | sudo tee /etc/sysctl.d/99-userns.conf
```

改完重跑自测那行，出 `OK` 再跑 demo。
**完全改不了 sysctl 时**：可 `sudo` 跑 `sl-node run`（root 写 uid_map 不受限，`SUDO_UID/GID` 会让 jailer 降回真实用户），或加 `--no-netns` 跳过 netns —— 但 orch/bind 私有 rootfs 路径同样依赖 userns，完整生命周期仍需开启。

### 5.2 `/dev/kvm` 相关

console.log 出现 `Error creating the KVM context ... No such file or directory`（无设备）或 `Permission denied`（无权限）。

```bash
ls -l /dev/kvm
[ -w /dev/kvm ] && echo OK || echo "缺失/不可写"
```

- 无权限：`sudo usermod -aG kvm "$USER"`，重新登录（或 `newgrp kvm`）。
- 无设备：需宿主机支持嵌套虚拟化（WSL2 见 `.wslconfig` 的 `nestedVirtualization=true` + `wsl --update`；云 VM 需选支持嵌套虚拟化的实例）。无 KVM 只能走 §4 "无 KVM 能做什么"。

### 5.3 Firecracker 拉取/版本

`build/firecracker/firecracker --version` 无输出 → 二进制损坏或架构不对（仅 x86_64）。重跑 `scripts/fetch-firecracker.sh` 或手动放置。
