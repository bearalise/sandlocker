# SandLocker 部署指南

把仓库 clone 到一个全新环境后，如何从零跑通。本文覆盖依赖安装、运行时工件构建、环境自检、运行方式，以及新环境最常踩的坑。

> 适用范围：单机开发 / 自部署起步（PRD §"自部署一等公民"）。当前里程碑 M1，架构为 Rust workspace + Firecracker microVM 后端。

---

## 0. 硬性前提

- **架构**：仅 x86_64（`fetch-firecracker.sh` / rootfs 均硬编码 `x86_64`）。
- **KVM**：起 microVM 必须 `/dev/kvm` 可写 —— 裸金属，或开启了嵌套虚拟化的 VM / WSL2。
  没有 KVM 仍可做：工作区编译、单元测试、guest 内核构建；但 demo / 生命周期 / 基准跑不了。
- **非特权 user namespace**：本项目网络与私有 rootfs 走 rootless（`unshare --map-root-user`），
  需要内核允许非特权 userns。见 §5 常见问题（Ubuntu 24.04 默认拦这个）。

`build/` 与 `target/` 都在 `.gitignore` 里 —— **clone 后 `build/` 是空的，运行时工件必须自己生成**（§2）。

## 1. 安装依赖

### 1.1 系统包

```bash
sudo apt-get update && sudo apt-get install -y \
  build-essential flex bison libelf-dev libssl-dev bc \
  e2fsprogs nftables iproute2 curl
```

| 包 | 用途 |
|---|---|
| `build-essential flex bison libelf-dev libssl-dev bc` | 构建 guest 内核（`scripts/build-kernel.sh`） |
| `e2fsprogs`（`mke2fs`） | 免 sudo 造 ext4 rootfs（`scripts/build-rootfs.sh`） |
| `nftables iproute2` | 网络后端 / netns / tap |
| `curl` | 拉 Firecracker、内核源码 |

### 1.2 Rust 工具链（含 musl target）

`sl-envd` 是 guest 里的 PID 1，要求 musl 静态链接，故必须额外装 `x86_64-unknown-linux-musl`。

```bash
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
. "$HOME/.cargo/env"                        # 让当前 shell 立即能用 cargo
rustup target add x86_64-unknown-linux-musl
```

验证：

```bash
cargo --version
rustup target list --installed | grep musl   # 应有 x86_64-unknown-linux-musl
```

> 项目无 `rust-toolchain.toml`，用 stable 即可（与 CI 的 `dtolnay/rust-toolchain@stable` 一致）。

**国内镜像（可选）**

- rustup（工具链下载），装 rustup **之前** export，建议写进 `~/.bashrc`：

  ```bash
  export RUSTUP_DIST_SERVER="https://mirrors.tuna.tsinghua.edu.cn/rustup"
  export RUSTUP_UPDATE_ROOT="https://mirrors.tuna.tsinghua.edu.cn/rustup/rustup"
  ```

- cargo（拉 crates），写入 `~/.cargo/config.toml`：

  ```toml
  [source.crates-io]
  replace-with = 'tuna'
  [source.tuna]
  registry = "sparse+https://mirrors.tuna.tsinghua.edu.cn/crates.io-index/"
  ```

## 2. 生成运行时工件

这两样是 microVM 的硬依赖，且被 gitignore，clone 后必须自己生成。

### 2.1 Firecracker 二进制

```bash
scripts/fetch-firecracker.sh            # 默认 latest；也可 scripts/fetch-firecracker.sh v1.16.1
```

产物：`build/firecracker/firecracker`、`build/firecracker/jailer`。
需能访问 GitHub；受限网络可手动下载对应 `firecracker-<版本>-x86_64.tgz`，解压后把两个二进制放进 `build/firecracker/` 并 `chmod +x`。

### 2.2 Guest 内核

```bash
scripts/build-kernel.sh                  # 默认 6.6
```

产物：`build/kernel/vmlinux-<版本>` + 软链 `build/kernel/vmlinux` + `.sha256` + `build-info.txt`。

- 以 Firecracker 官方 guest config（6.1 基线）为起点，叠加 `scripts/kernel-fragment.config`
  （vmgenid / vsock / dm-thin 等必需项），`olddefconfig` 适配后编译。
- **耗时最长**（几分钟到十几分钟，取决于核数）；**不需要 KVM**。
- 系统缺 `flex/bison/m4`/libelf 头时会回退到仓库内 `.toolchain/`（若存在）。

## 3. 环境自检

```bash
scripts/bench/check-env.sh
```

逐项检查 `kvm` / `firecracker` / `guest_kernel`，任一缺失即非零退出。
**先过这一步再跑 demo**，能提前拦住"直接 run-demo 才发现缺 KVM/工件"的弯路。

## 4. 运行

先把工作区编出来：

```bash
. "$HOME/.cargo/env"
cargo build --release -p sl-node
cargo build --release -p sandlocker
cargo build --release -p sl-envd --target x86_64-unknown-linux-musl
```

### 路径 A：端到端 demo（先验通链路，最省事）

```bash
scripts/run-demo.sh
```

自动：编 `sl-node` → 编 `sl-envd`(musl) → 造 rootfs → 起 microVM 做 host↔guest vsock echo。
**要 KVM + userns**。看到 `W4 demo PASS` 即整条链路 OK。

### 路径 B：用户面 CLI（`sandlocker`，纯 REST 客户端）

```bash
# 1) 起守护（前台，默认 127.0.0.1:7878）；实为 sl-node --serve
./target/release/sandlocker up

# 2) 另开终端
./target/release/sandlocker build examples/hello.sandlocker.toml
./target/release/sandlocker run <template>
./target/release/sandlocker ps
./target/release/sandlocker exec <id> -- <cmd>
./target/release/sandlocker logs <id>
./target/release/sandlocker snapshot <id>
```

> `sandlocker` 的 `up`/`build` 会转发到**同目录的兄弟 `sl-node` 二进制**，两者需在同一 `target/release/`。
> 契约见 `contracts/openapi.yaml`。

### 路径 D：Python SDK（`sandlocker` 包，纯 stdlib）

给终端用户的编程接口（PRD 7.6）。零第三方依赖，契约见 `contracts/openapi.yaml`，详见 `sdk/python/README.md`。

```bash
# 1) 起守护 + 备一个模板
./target/release/sandlocker up &                             # 默认 127.0.0.1:7878
./target/release/sandlocker build examples/hello.sandlocker.toml

# 2) 装 SDK（或免安装用 PYTHONPATH）
pip install -e sdk/python          # 方式一
export PYTHONPATH="$PWD/sdk/python/src"   # 方式二（免安装）

# 3) 三行手感
python3 - <<'PY'
from sandlocker import Sandbox
with Sandbox.create(template="hello", timeout=300) as sbx:
    print(sbx.run("echo hi").stdout, end="")
PY

# 4) 或跑用户故事场景（US-1/US-4/US-7）
export SANDLOCKER_ADDR=127.0.0.1:7878
python3 examples/sdk/us1_quickstart.py    # 创建→跑分析→取产物→空闲自动销毁
python3 examples/sdk/us4_template.py      # 团队模板 + 秒级就绪
python3 examples/sdk/us7_ci_ephemeral.py  # CI 跑不可信测试，退出码透传 + 跑完即焚
```

> **M1 边界**：基座 rootfs 是 busybox（**无 Python 解释器**），且模板构建 deny 网络（无法 pip）。
> 故示例用 busybox shell 命令演示；真正的「Python + pandas」团队模板需 M2 的 allow-network 构建。详见 `sdk/python/README.md`。

一键门禁（自动起守护、跑三场景、断言零残留；KVM/python3 缺失则跳过退 0）：`scripts/verify-sdk-e2e.sh`。

### 路径 C：底层 `sl-node` 直接对账（CI 用的回归命令）

默认路径已内置（`build/kernel/vmlinux`、`build/rootfs/rootfs.ext4`、`build/firecracker/firecracker`）。

```bash
# 模板构建（rootless，deny 网络离线，无需 root）
./target/release/sl-node --build examples/hello.sandlocker.toml --json

# 生命周期对账（要 KVM）；先 --build 拿 <version>
./target/release/sl-node --orch-reconcile build/templates/hello/<version> --json

# 存储 / 网络对账（要 root）
sudo ./target/release/sl-node --dmthin-reconcile --cycles 5 --json
sudo ./target/release/sl-node --nftfw-reconcile --json
```

常用参数（`parse_args`）：`--kernel/--rootfs/--fc/--jailer/--workdir` 覆盖路径，
`--boot api|config-file|jailer`、`--no-netns`、`--json`、`--cycles N`、`--hold-secs N`。

### 无 KVM 环境能做什么（等价 CI 的 `validate` job）

```bash
for f in scripts/*.sh scripts/bench/*.sh; do bash -n "$f"; done   # 脚本语法检查
cargo build --workspace --release
cargo test -p sl-proto -p sl-node -p sl-store -p sandlocker        # Rust 单元测试
python3 -m unittest discover -s sdk/python/tests                    # Python SDK 单测（假 daemon）
scripts/build-kernel.sh                                             # 内核构建不需 KVM
```

## 5. 常见问题（FAQ）

排障总入口：microVM 相关失败先看 **`build/run/console.log`**（FC 的 stdout/stderr + guest 串口 + sl-envd 日志）。

### 5.1 `unshare: 写失败：/proc/self/uid_map: 不允许的操作`

**现象**：`run-demo.sh` 报 `FC 在 API 就绪前退出（status=1）`，console.log 首行是上面这句。
**根因**：本项目网络/私有 rootfs 走 rootless（`unshare --net --map-root-user`），而内核禁用了非特权 user namespace。

先定位是哪种禁用：

```bash
sysctl kernel.unprivileged_userns_clone            # 应为 1
sysctl kernel.apparmor_restrict_unprivileged_userns # Ubuntu 24.04 默认 1 → 就是它
sysctl user.max_user_namespaces                    # 应 > 0
unshare --user --map-root-user true && echo OK || echo BLOCKED   # 自测
```

对应修复：

| 查到 | 修复 |
|---|---|
| `apparmor_restrict_unprivileged_userns = 1`（Ubuntu 23.10+/24.04 最常见） | `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0` |
| `unprivileged_userns_clone = 0`（Debian/老 Ubuntu） | `sudo sysctl -w kernel.unprivileged_userns_clone=1` |
| `user.max_user_namespaces = 0` | `sudo sysctl -w user.max_user_namespaces=15000` |

永久生效（示例 apparmor 那条）：

```bash
echo 'kernel.apparmor_restrict_unprivileged_userns=0' | sudo tee /etc/sysctl.d/99-userns.conf
```

改完重跑自测那行，出 `OK` 再跑 demo。
**完全改不了 sysctl 时**：可 `sudo` 跑 `sl-node run`（root 写 uid_map 不受限，`SUDO_UID/GID` 会让 jailer 降回真实用户），或加 `--no-netns` 跳过 netns —— 但 orch/bind 私有 rootfs 路径同样依赖 userns，完整生命周期仍需开启。

### 5.2 `/dev/kvm` 相关

console.log 出现 `Error creating the KVM context ... No such file or directory`（无设备）或 `Permission denied`（无权限）。

```bash
ls -l /dev/kvm
[ -w /dev/kvm ] && echo OK || echo "缺失/不可写"
```

- 无权限：`sudo usermod -aG kvm "$USER"`，重新登录（或 `newgrp kvm`）。
- 无设备：需宿主机支持嵌套虚拟化（WSL2 见 `.wslconfig` 的 `nestedVirtualization=true` + `wsl --update`；云 VM 需选支持嵌套虚拟化的实例）。无 KVM 只能走 §4 "无 KVM 能做什么"。

### 5.3 Firecracker 拉取/版本

`build/firecracker/firecracker --version` 无输出 → 二进制损坏或架构不对（仅 x86_64）。重跑 `scripts/fetch-firecracker.sh` 或手动放置。

## 6. 一页速查（TL;DR）

```bash
# 1. 依赖
sudo apt-get update && sudo apt-get install -y build-essential flex bison libelf-dev libssl-dev bc e2fsprogs nftables iproute2 curl
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh && . "$HOME/.cargo/env"
rustup target add x86_64-unknown-linux-musl

# 2. 运行时工件（build/ 是 gitignore 的，必须自己造）
scripts/fetch-firecracker.sh
scripts/build-kernel.sh

# 3. 若是 Ubuntu 24.04：先开 rootless userns（最常见的坑）
sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0

# 4. 自检 + 跑通
scripts/bench/check-env.sh
scripts/run-demo.sh          # 看到 "W4 demo PASS" 即成功
```
